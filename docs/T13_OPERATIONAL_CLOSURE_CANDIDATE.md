# T13.7 — operacionalização candidata
Não certificada nem autorizada para promoção. Preserva o SaaS interno em outro runtime. O rollout exige o usuário exclusivo, socket rootless e diretório /opt/atendevendeia-t13-runtime; usa projeto Compose explícito e porta loopback 18080. Não utilizar Docker administrativo. O host deve ser previamente provisionado por operador autorizado. O daemon exclusivo ainda não está ativo.
A autorização de worker (T13_WORKER_AUTHORITY_CONFIRMED=true, arquivo privado do operador) só pode ser estabelecida após inventário do Cloud Run histórico e ausência de concorrência, sem alteração automática de dados ou tráfego. O rollout valida API e worker por saúde e referência imutável, mantém o digest anterior, reverte ambos após erro e para somente serviços candidatos quando não existe release anterior. Não reverte escritas de banco; primeira falha exige inspeção/limpeza explícita do projeto isolado.
O CI usa token curto da conta t13-rules-verifier, via Workload Identity Federation. Configurar variáveis T13_RULES_WIF_PROVIDER e T13_RULES_SERVICE_ACCOUNT no ambiente protegido, restringir atributo do provedor à identidade numérica do repositório e owner, workflow de deploy exato, main e environment t13-production-approval; conceder somente impersonação do verificador e leitura das regras + serviceUsageConsumer no projeto de quota. Nenhuma chave administrativa ou token permanente no GitHub. Provisionamento e teste remoto ainda pendentes. Runtime Firebase permanece identidade própria; conceder somente escopos necessários, sem copiar chaves da FM.
Candidata exige CI integral e revisão independente nova; o parecer histórico não cobre estas mudanças. Não modificar a política de auditoria para aceitar uma evidência antiga. Domínio/HTTPS, conectividade SSH do runner, daemon e credenciais próprios, índice/Auth/Firestore, testes de worker e post-deploy reais continuam gates. T14 permanece bloqueada para promoção até fechamento T13.7. Nenhuma ativação comercial autorizada.

O projeto Firebase do runtime precisa coincidir com o projeto verificado pelo gate CI; divergência bloqueia o rollout antes do Docker. Tempo máximo do job ampliado para acomodar health e rollback, sem remover gates.

A topologia de produção exige os quatro parâmetros públicos do Firebase Web; a implantação confere o projeto web e o endpoint /api/runtime/firebase-web antes de iniciar o worker. Configuração pública de Firebase não é autenticação administrativa nem prova de login. A identidade dedicada de verificação WIF, seus vínculos IAM mínimos e variáveis do ambiente protegido foram provisionados em 24/11/2026; troca de token OIDC ainda precisa de prova real no workflow protegido.
